# SCN-10-1 — Approve OD-2: Apple sign-in requirement for native app

> Type: documentation · Date: 2026-09-30

## Context

SLAY CITY's web app implements Google sign-in (`signInWithGoogle`,
`src/features/auth/actions.ts` in `rubanwd/slay-city`). The native iOS build
of the same product cannot ship that without also offering Sign in with
Apple: App Store Review Guideline 4.8 requires an equivalent third-party login
option whenever an app offers one, and reviewers check this by hand at
submission. `docs/RISKS.md` `R2` already carried this at 🟠 high, and
`docs/ROADMAP.md` and `docs/WORK-PACKAGES.md` already gated `M2` and
`WP-2.5` on an open decision, `OD-2`, that nobody had formally answered yet.
This item is that answer: read Guideline 4.8, confirm the requirement in
writing, decide between the two options the planning docs had already listed,
and record `OD-2` as approved so `WP-2.5` (social sign-in, M2) can be scoped
without a caveat.

It is a documentation-only decision, the same shape as `SCN-7`'s `OD-1`
(OpenRouter Edge Functions): no source code, no `packages/core` change, no
migration.

## What was done

### 1. Read the requirement and the existing planning material

`docs/ARCHITECTURE.md` §7, `docs/CONCEPT.md` §10, `docs/RISKS.md` `R2`,
`docs/ROADMAP.md`'s dependency graph and M2 section, and `docs/WORK-PACKAGES.md`
`WP-2.5` all already described `OD-2` with the same two options — (a)
implement Sign in with Apple, (b) hide Google on iOS — and the same
recommendation, (a). None had marked it decided.

### 2. Verified the actual auth screens against `upstream/`, not the ticket's assumption

The ticket asked to list "student onboarding, teacher onboarding, parent
onboarding" as the screens needing both sign-in options. Reading
`upstream/src/features/auth/AuthForm.tsx`, `upstream/src/app/auth/login/page.tsx`,
`upstream/src/app/auth/register/page.tsx`, `upstream/src/features/auth/actions.ts`
and `upstream/src/features/auth/roleRouting.ts` shows this does not match the
web app's structure: there is **one shared `AuthForm`** backing exactly two
routes (`/auth/login`, `/auth/register`), and the Google button renders in
both regardless of role. `SignupRole` is `"student" | "parent"` only — there
is no self-service teacher signup. `upstream/AGENTS.md`: *"The `teacher` role
... is promotion-only (an admin flips an existing account's role via
`promote_teacher()`)"* — a future teacher registers as a student on the same
register screen and is promoted server-side afterward. Parents are
auto-provisioned on first sign-in (`ensureRoleProfile()`); there is no
separate parent onboarding screen either. `app/onboarding.tsx`
(`OnboardingForm`) is student-only profile setup (username/age/level) that
runs after a session already exists and contains no sign-in action of its
own.

`docs/OD-2-DECISION.md` §3 records both the requested per-role breakdown
(student/teacher/parent, in a table) **and** the correction: the two screens
that actually need both sign-in options are the shared login and register
screens, because every role passes through them.

### 3. Wrote `docs/OD-2-DECISION.md` and recorded OD-2 as APPROVED

**OD-2 — APPROVED, 2026-09-30. Option (a): implement Sign in with Apple.
Rationale: Guideline 4.8 is a hard App Store review requirement, not a
recommendation.** Option (b) (hide Google on iOS) is recorded as rejected,
with the reason: it would leave a web-created Google account unable to sign
in from an iPhone at all.

The document also explains why the *web* app is exempt (Guideline 4.8 is an
App Store review rule; the web is a desktop/browser product on Vercel, never
submitted to App Store review), and why, unlike `OD-1`, approving `OD-2`
needs **no upstream pull request**: the root manual's "Apple OAuth: Do Not
Build Yet" line is a web-scoped product-scope choice, not a security
invariant, so it is overridden locally in this repository's own `AGENTS.md`
rather than amended in `rubanwd/slay-city`.

## Technical decisions

- **Two screens, not three.** The ticket's acceptance criteria named
  "student onboarding, teacher onboarding, parent onboarding." Reading the
  actual auth code shows one shared login screen and one shared register
  screen serve all three roles — there is no self-service teacher signup
  (promotion-only) and no separate parent onboarding form (auto-provisioned).
  Rejected inventing three screens to match the ticket's wording literally,
  because that would misrepresent the codebase the way `SCN-6`/`SCN-7` found
  and corrected inaccurate file/write counts in earlier planning docs.
  Documented the correction explicitly rather than silently deviating from
  the ticket text, and still answered the underlying question (which roles
  need coverage, and where) via a role-to-screen table.
- **No upstream pull request, unlike `OD-1`.** `OD-1` changed a security
  invariant the root manual locks ("never expose the key"), so the amendment
  had to land with the code, upstream. `OD-2`'s root-manual line ("Apple
  OAuth: Do Not Build Yet") is a product-scope decision made for the web MVP,
  where Apple sign-in has no purpose — the web is never App-Store-reviewed.
  Overriding it doesn't touch anything the web app does, so the override is
  recorded only in this repository's own `AGENTS.md`, and no PR against
  `rubanwd/slay-city` is proposed.
- **Option (a) over (b), with the rejection reason stated.** (b) — hiding
  Google on iOS — was rejected because it creates a worse problem than the one
  it avoids: an account made with Google on the web becomes unable to sign in
  from an iPhone at all, which is a retention/support cost the product does
  not have today.

## Limitations and follow-ups

- **No code is implemented.** This is a decision record, as the ticket
  specifies. Apple sign-in itself is `WP-2.5`, in M2.
- **`WP-2.5`'s exact client-side flow (SDK, nonce handling, button styling)
  is not specified here.** That level of detail belongs in `WP-2.5`'s own
  scoping, the way `EDGE-FUNCTIONS-PLAN.md` did for `WP-5.6` — this document
  only answers whether and where, not how.
- **Everything is read from `rubanwd/slay-city` at `7612da5`.** If the web
  app's auth screens or role model change before `WP-2.5` starts, re-verify
  §3's screen table against current `upstream/` first.
- **`RISKS.md`'s M7 compliance checklist item ("Sign in with Apple, or no
  third-party login on iOS") is left unchecked.** It becomes checkable only
  once `WP-2.5` ships, not by this decision.
