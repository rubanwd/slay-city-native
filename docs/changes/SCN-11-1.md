# SCN-11-1 — Decide canonical profiles.age range: DB (7–14) vs onboarding form (5–99)

> Type: task · Date: 2026-09-30

## Context

`SCN-6`'s write audit and `SCN-11`'s implementation of `create_my_profile()`
both ran into the same open disagreement: the web app's `profiles.age` column
carries `check (age is null or age between 7 and 14)`
(`20260703000001_add_profile_age.sql`), while
`features/onboarding/actions.ts` has validated and displayed `MIN_AGE = 5` /
`MAX_AGE = 99` since commit `32247f5` (#91). A user entering 5, 6, or anything
from 15 up passes the form and then hits a raw `23514` Postgres constraint
error on submit — a pre-existing web bug, not a security issue, but one that
`create_my_profile()` could not encode a fix for without a product decision:
picking a side inside that function would have silently made either the form
or the column wrong. `SCN-11`'s change summary and
`docs/UPSTREAM-PR-WP-2.3.md` both left this as the one open item blocking the
staged pull request. This item's job was to settle it and record the answer
so `SCN-11`'s migration set can close it out.

## What was done

Decided the form's range — **5 to 99 inclusive, still nullable** — is
canonical, and the DB constraint is the side that moves.

The deciding fact: `age` is a purely write-only field. It is collected once
during onboarding, inserted into `profiles.age`, and never read back —
confirmed by grepping both this repository and the upstream web app
(`upstream/` at commit `7612da5`) for `\bage\b` outside
`features/onboarding/actions.ts`, `features/onboarding/OnboardingForm.tsx` and
the generated `types/database.ts` row type. No screen (student, teacher,
parent or admin), no RPC, no mission/knowledge-level gate and no XP/streak
rule conditions on it. That removes the main risk a range change could carry
— since nothing downstream branches on age, widening the column cannot open
an age-gated feature to the wrong cohort, and narrowing the form to 7–14 would
have a real cost: it would reject a parent completing onboarding on their
child's behalf, or an adult learner, both of which the product currently
allows and neither of which the 7–14 constraint was written to exclude (its
own comment says "constrained to the product's target age range," not "the
DB is authoritative over the form").

With that decided, the one line of SQL the audit and the PR body had already
drafted as the "widen" branch was written as a fifth migration in
`docs/migrations/wp-2.3/`, alongside the four from `SCN-11`:

```sql
alter table public.profiles
  drop constraint profiles_age_check,
  add constraint profiles_age_check check (age is null or age between 5 and 99);
```

`profiles_age_check` is Postgres's default name for the column's originally
unnamed, single-column CHECK — confirmed by reading
`20260703000001_add_profile_age.sql`, which declares it inline with no
explicit constraint name.

Because the new range is a superset of the old one, no existing row can
violate it — there is no backfill or data cleanup to do, unlike the
`user_stats` backfill `SCN-11`'s migration 3/4 needed. The change is purely
additive in effect, even though it is written as drop-then-add because
Postgres has no "alter constraint" for a CHECK expression.

`create_my_profile()` (from `SCN-11`, migration 3/4) is unchanged in
behaviour: it already passed `p_age` straight through to the column's own
CHECK rather than re-validating the range itself, which was the correct
design regardless of which way this decision went — the column CHECK is the
single source of truth for the range, and duplicating it in the function
would only create a second place for the two ranges to disagree again later.
Its comments were updated to point at this decision instead of describing it
as open.

All five migrations, four supporting documents
(`docs/UPSTREAM-PR-WP-2.3.md`, `docs/MIGRATIONS-NEEDED.md`,
`docs/migrations/wp-2.3/README.md`, `docs/changes/SCN-11.md`) that referenced
the open decision were updated to record it as resolved, so a reader of any
one of them sees the same answer without needing to find this file first.

## Technical decisions

- **Widen the DB to 5–99 rather than narrow the form to 7–14.** The
  alternative — tightening `MIN_AGE`/`MAX_AGE` in
  `features/onboarding/actions.ts` and its picker — was rejected because `age`
  gates nothing downstream, so there is no protective reason to exclude 5, 6
  or 15–99, and narrowing would visibly reject users (a parent onboarding for
  a child, an adult learner) the product currently accepts through the form
  without complaint. Widening has no such cost because the value is never
  read back.
- **No re-validation of the range inside `create_my_profile()`.** Keeping the
  column's CHECK as the only place the range is expressed, rather than also
  checking it in the function (the way username and level *are* re-checked in
  SQL), avoids recreating exactly the two-sources-of-disagreement bug this
  item exists to close. If the range ever needs to change again, one
  migration is sufficient.
- **A fifth migration, not a rewrite of `SCN-11`'s existing files.** The four
  migrations from `SCN-11` were already written, tested (61 `PASS` in
  `tests/negative-tests.sql`) and documented as a unit; folding an unrelated
  column constraint into one of them would have mixed an independent, always-
  safe-to-apply change into a set whose 4/4 is a deliberate breaking
  lockdown. A fifth file that can be applied in any order relative to the
  other four keeps that property.
- **Drop-then-add CHECK, not a data migration.** Postgres has no syntax to
  widen a CHECK expression in place; `alter table … drop constraint …, add
  constraint …` is the standard idiom. Since 5–99 is a superset of 7–14, this
  cannot fail against any row that satisfied the original constraint.

## Data, API and configuration

**No change to this repository's schema, dependencies, configuration, or any
TypeScript source.** Everything changed is SQL staged for the web repository
and documentation.

For the web repository, when `docs/migrations/wp-2.3/20260930000005_widen_profile_age_range.sql`
is applied there:

- **Constraint change**: `public.profiles`'s `profiles_age_check` CHECK
  widens from `age is null or age between 7 and 14` to `age is null or age
  between 5 and 99`. No column, policy, grant, function or trigger is added,
  altered or dropped.
- **No backfill required.** The new range is a strict superset of the old
  one.
- `features/onboarding/actions.ts`'s existing `MIN_AGE = 5` / `MAX_AGE = 99`
  needs no code change — it already matches the range the column now
  enforces; today it is the column that is out of step, not the action.

## How to verify

- Read the new migration and its rollback
  (`docs/migrations/wp-2.3/20260930000005_widen_profile_age_range.sql`,
  `docs/migrations/wp-2.3/down/20260930000005_widen_profile_age_range_down.sql`)
  — both are single `alter table` statements, reviewable by inspection.
- Confirmed by search that `age` has no downstream reader: `grep -rn
  "\bage\b"` across `upstream/src` and `packages/core/src` returns matches
  only in `features/onboarding/actions.ts`, `OnboardingForm.tsx`,
  `types/database.ts`'s generated types, and file-path false positives (e.g.
  `profile/page.tsx` matching on "page"), confirmed individually with
  word-boundary greps against each candidate file (`ParentDashboard.tsx`,
  `ParentProfileScreen.tsx`, `parent/queries.ts`, `admin/userActions.ts`,
  `app/profile/page.tsx`) — none reference `age`.
- `npm run type-check` was run: it reports the same pre-existing failure
  already recorded in `SCN-11`'s change summary
  (`packages/tokens/src/typography.ts` declares `fluidFontSize` twice), which
  predates this item and is untouched by it — `git diff HEAD --
  packages/tokens/` is empty. This item added only SQL and Markdown, so there
  is nothing here for `npm run lint` or `npm test` to check either.
- Manual: once the migration set is applied on a branch database, submitting
  the onboarding form with age 5, 6, 15 or 99 should succeed where it
  previously raised `23514`; ages outside 5–99 (e.g. 4 or 100) should still be
  rejected, first by the form's own `MIN_AGE`/`MAX_AGE` check and, if that
  were ever bypassed, by the column's CHECK as a second line of defence.

## Limitations and follow-ups

- **Not applied anywhere.** Like the rest of `docs/migrations/wp-2.3/`, this
  migration is staged documentation for a pull request against
  `rubanwd/slay-city` that has not been opened. `SCN-11`'s own *How to
  verify* section is the place a live-database replay of 1/4–4/4 was actually
  run; this item's migration was reviewed by inspection, consistent with the
  other four not being re-run for this change.
- **Does not touch `features/onboarding/actions.ts`.** No code change was
  needed there — its `MIN_AGE`/`MAX_AGE` already match the decided range —
  but a human opening the upstream PR should still confirm the action and
  its picker UI show 5–99 as the full round trip, since this item only
  verified the constraint and the action's constants, not the UI copy.
- **`SCN-11`'s other follow-ups are untouched by this item**: the
  `profiles.username` table-level CHECK, the `vocab_image_cache` /
  `content/homework/` cross-teacher exposure (F5), and the already-forged
  `user_stats` cleanup (U-3) all remain open, as recorded in
  `docs/changes/SCN-11.md`.
